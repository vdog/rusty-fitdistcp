## Fairness caveats

1. **Optimizer algorithm differs.** The reference R package uses `optim` (Nelder–Mead); the Rust port uses BFGS + Newton. This is an algorithmic difference that dominates the end-to-end `predict` numbers.
2. **Interpreted vs compiled.** The Python module is pure Python; the Rust port is compiled. Pointwise operations show a large constant-factor gap that is a language/runtime effect.
3. **Monte Carlo reltest.** reltest is stochastic; the implementations are matched on `ntrials`/`nx`/`params` and use a fixed seed where possible. Residual differences are sampling noise.
4. **Parameterization.** The reference gamma uses `(shape, scale)`; the Rust port uses `(shape, rate)`. The harness converts so the same distribution is fit.
5. **Criterion vs wall-clock.** Criterion numbers and the CSV `Instant` numbers may differ slightly; the CSV is the cross-implementation source.
6. **Gamma domain restriction.** The shared grid.x spans [-3, 3], but the gamma distribution has support x > 0. The reference R and Python gamma routines reject non-positive x, so the gamma pdf/cdf/rvs workloads are evaluated on the strictly-positive subset of the grid (x > 0, 49 of 100 points) in all three harnesses. ppf and predict are unaffected; the (model, operation, n) keys are identical.
7. **R timer resolution.** R's proc.time() elapsed has ~1 ms resolution, so the R harness times a calibrated batch of calls per sample and divides by the batch size. Sub-millisecond workloads are therefore quantized to roughly 1 ms / batch_size.
